# Three Shape V2.9：开发规则、游戏玩法与经济模型

整理依据：当前原生 BNB 版 Solidity 源码与用户确认规则。Star 每售 1,000 枚上涨 0.005 BNB；测试网已部署与验证，主网未部署。测试明细见 reports/BNB_TESTNET_VALIDATION.zh-CN.md。

## 1. 项目定位与开发边界

Three Shape 是嵌在 Agent 对话消息中的交互游戏卡片。用户在同一条卡片消息内完成钱包连接、领取、收藏查看、挑战和奖励操作；普通聊天消息的新增不应重建游戏卡片。

技术交付采用 React + TypeScript、独立 CSS、可复用组件及 Adapter。游戏 UI 不直接调用合约，所有 RPC、ABI 编解码、钱包事件和交易确认集中在适配层。前端业务接口不等于 Solidity 函数签名，不能仅因名称相近就直接绑定。

- Mock 无需真实钱包或 ABI，必须显著标记模拟，不得宣称链上验证。
- Live 结果、阶段、余额、可领取资格、剩余份额和结算均以合约为准。
- 动画只表达等待，不能生成随机数、决定中奖或凭动画结束宣布交易成功。
- 交易由用户钱包签名，不索取或存储私钥；BNB 支付金额、gas 和操作影响必须向用户明确。
- 销毁前展示实际 NFT ID、当前剩余份额及不可逆风险，取得本次操作确认，再请求钱包签名。
- 处理拒签、交易失败、账户变化、网络变化和刷新恢复；待核实交易不得盲目重复发送。
- 不能擅自修改 Token 上限、奖励金额、份额、星星价格、LP 规则或添加管理员铸币权限。
- 已授权处理的编译、元数据、资格接入和部署适配，不能成为改变经济规则的理由。
- MysteryPortal 仅为 UI 占位与未来扩展入口，不公开解锁规则、奖励或空投数量，不实现信誉铸造或代币锁仓。
- 当前版本没有正式实现随机抽奖、失败重置、挑战重开或保底机制，不得在前端自行加入。

## 2. 五个业务合约

| 合约 | 职责 |
| --- | --- |
| Token | ERC20 3SHAPE，分别约束玩家铸币和 LP 铸币 |
| NFT | ERC721 水果与星星；由 Game 铸造和按规则销毁 |
| Game | 免费领取、个人挑战状态、份额、奖励领取、星星购买 |
| Reserve | 接收购星款的 80%，销售期间向指定 Liquidity 提供 BNB，售罄后可向固定 T 结算剩余 BNB |
| Liquidity | 根据单次额度和池比率加 LP，将 LP 凭证发送至销毁地址 |

部署工厂用于安排合约依赖，不属于第六种游戏经济角色。当前源码没有 ownerMint、adminMint 或管理员提款函数。

## 3. NFT 类型与免费领取

| kind | Emoji | 类型 |
| --- | --- | --- |
| 1 | 🍏 | Green Apple / 青苹果 |
| 2 | 🍋 | Lemon / 柠檬 |
| 3 | 🍇 | Grapes / 葡萄 |
| 4 | 🍒 | Cherries / 樱桃 |
| 5 | 🍓 | Strawberry / 草莓 |
| 6 | 🍐 | Pear / 香梨 |
| 7 | 🥭 | Mango / 芒果 |
| 8 | 🍉 | Watermelon / 西瓜 |
| 9 | 🌟 | Star / 星星 |

免费领取要求：奖励份额尚未耗尽、该钱包从未免费领取、指定 .ai Agent ID NFT 的 balanceOf(wallet)>0。无需另部署 Registry 适配合约，当前源码中 registry 变量直接指向该 NFT 合约。

每钱包免费领取一次，每次 3 枚普通水果 NFT。免费领取不收 BNB，但仍需链上 gas。星星不由这个入口发放。

免费领取由合约发放水果 NFT，不承诺领取后立即满足三同条件。交互信息和玩法介绍不展示发放的内部顺序，也不宣传为随机抽奖。玩家可通过收集或转让凑齐挑战条件。

免费领取、销毁挑战、继续挑战、领取奖励和购买 Star，五个链上操作均检查当前调用钱包的 .ai Agent ID 余额。查看公开链上数据不属于付费或奖励操作；BNB 购星不需要 ERC20 授权。资格按钱包当前持有情况校验，不绑定身份 NFT 编号，不消耗或锁定身份 NFT；这不是完整的多钱包防刷证明。

免费 NFT 总量没有单独的固定上限。55,000 是成功领奖份额数，不是免费领取钱包名额。

## 4. 个人三档挑战

| 个人档位 | 本档独立销毁条件 | 成功后选择 |
| --- | --- | --- |
| 第一档 | 恰好 3 枚 NFT，允许 Star 补齐；至少 1 枚普通水果且普通水果必须同种 | 领取本档奖励，或继续第二档 |
| 第二档 | 恰好 6 枚 NFT，至少 1 枚星星；所有普通水果同种且至少有 1 枚普通水果 | 领取本档奖励，或继续第三档 |
| 第三档 | 恰好 9 枚 NFT，至少 3 枚星星；所有普通水果同种且至少有 1 枚普通水果 | 领取第三档奖励 |

所有提交的 NFT 必须属于当前钱包，ID 不可重复。第二档不是必须 5 水果+1星，而是允许更多星星；第三档也不是只能 6水果+3星。

每档都是新的一组销毁。第二档完整路径消耗 3+6=9 枚 NFT；第三档完整路径消耗 3+6+9=18 枚 NFT，至少消耗 4 枚星星。

继续挑战不发放上一档 Token。奖励不累加；一个钱包成功领取任意一档后进入 Settled，不能再次领奖，当前没有重开函数。

个人状态路径：Ready1 → Choice1 → Ready2 → Choice2 → Ready3 → Choice3 → Settled。其中每个 Choice 状态可按规则领取并直接进入 Settled；Choice1、Choice2 可选择继续。

从销毁到领取，每一步都必须继续持有 .ai Agent ID；失去持有资格时不能继续操作，已经成功销毁的 NFT 不会因此自动恢复。

销毁成功不消耗领奖份额，也不预留份额。成功领奖才将 totalClaims 加一。领取时按当时全局阶段计算金额，并检查 minAmount；金额低于用户最低可接受值则交易回退。

销毁交易失败会整体回退，不应扣 NFT 或推进进度。但是已经成功销毁后，后续领奖失败不会自动恢复先前销毁的 NFT。其他钱包可能在此期间领完最后份额。

## 6. Token 模型

名称 Three Shape，符号 3SHAPE，精度 18。

| 铸币用途 | 硬上限 | 释放方式 |
| --- | --- | --- |
| 玩家奖励 | 1,430,000,000,000，即 1.43 万亿 | 成功领奖时由 Game 铸造 |
| LP | 1,430,000,000,000，即 1.43 万亿 | Liquidity 在成功加池调用中按需要铸造 |
| 总计 | 2,860,000,000,000，即 2.86 万亿 | 两部分分别受限，不能挪用额度 |

部署时没有预铸玩家奖励。NFT 销毁、选择继续、前端动画均不会直接发放奖励。份额结束后未使用的玩家铸币额度没有补发入口。

上限不等于一定全部发行。特别是：完成三档路径至少销毁 4 枚星星，而星星总量只有 100,000；即使全部用于第三档路径，最多也只能支持 25,000 个第三档领奖钱包。因此不能把 55,000 份额理解为 55,000 人都可拿第三档奖励，也不能把玩家 cap 当作必然释放量。

## 7. 星星销售与 BNB 分账

星星总销售上限 100,000 枚。每次购买 1–6 枚，每钱包累计购买最多 6 枚；销毁或转出不重置购买次数。接收转来的星星不等于新增购买额度。

价格由全局累计已售数量决定，跨档购买逐枚累计报价；maxPayment 用于防止实际花费超过用户确认额度。

| 星星销售序号 | 单价 BNB |
| --- | --- |
| 1–1,000 | 0.01 |
| 1,001–2,000 | 0.015 |
| 2,001–3,000 | 0.02 |
| … | 每个区间增加 0.005 |
| 98,001–99,000 | 0.5 |
| 99,001–100,000 | 0.505 |

每笔购星款：80% 转入 Reserve，20% 转入 Treasury。使用原生 BNB，以 18 位整数 wei 结算；msg.value 必须精确等于执行时报价。

若 100,000 枚全部按上述价格售出，总销售额为 25,750 BNB，Reserve 累计流入 20,600 BNB，Treasury 累计流入 5,150 BNB。Reserve 的「流入」不等于最终余额，因为其中资金可能已用于加池。

## 8. LP 机制

每卖出 1 枚星星，只为该笔购买解锁最多 14,300,000 枚 3SHAPE 的一次性铸币额度。买多枚时本次额度相应相乘。100,000×14,300,000=1.43 万亿，是 LP cap 的来源。

首次加池要求交易对为空，包括 reserves 和 LP totalSupply 均为零。初始比例固定为 0.008 BNB : 14,300,000 3SHAPE，即 1 BNB 对应 1,787,500,000 3SHAPE；这只是初始加池比例，不是价格保底。

后续加池按当前交易对储备比例计算，优先匹配 Reserve 中可用 BNB，实际铸币不超过本笔销售新解锁的额度。未使用的 BNB 保留在 Reserve，可参与后续购买触发的加池。

Reserve 余额不保证最终全部入池：Star 售罄且最后一次加池尝试结束后，任何人可通过独立的 settleToTreasury() 将剩余 BNB 全部结算给固定 T。最后一次 LP 失败不阻止售罄结算，余额不再保证用于 LP，已过期铸币额度不会恢复。T 拒收则本次结算回滚、资金留存，可重试；没有管理员或可变收款地址。已发布旧部署不支持新增结算，新版需重新部署。举例而言，若池比例始终保持初始比例且每枚 Star 都用满 LP 铸币额度，100,000 枚合计加池只使用 800 BNB；按新价格模型 Reserve 累计流入 20,600 BNB，结算前仍会剩余 19,800 BNB，该余额按最终结算规则转入 T。该例依赖没有交易或其他操作改变池比例的假设，不能当作实际最终余额预测。

未使用的 Token 铸币额度在当次尝试结束后立即过期，不累计到下一笔。失败尝试也使整笔额度过期，但不会让已铸造 Token 被重复计算或回收。

LP 子调用失败时，子调用内的资金移动和铸币回退；Game 捕获失败并发出 LPAttemptFailed。星星购买和分账可以成功，80% 的本次购星款保留在 Reserve；前端不能把「购星成功」等同于「LP 成功」。

lpBudgetExpired 累计的是已经走过本次尝试、因而过期的完整预算，包括成功尝试的预算，不等于实际 LP 铸币量。实际量应读取 token.lpMinted()/lpMintedActual()。

LP 凭证直接发送至 0x000000000000000000000000000000000000dEaD。这里是发送至销毁地址，不应描述成合约调用了 LP burn 函数；也不是新增用户代币锁仓产品。

当前池现货比率可被操纵是现有设计的已知取舍。现有 addLiquidity 最低使用量检查不能据此解释成独立价格预言机或 TWAP 保护。

## 10. 后续开发必须对齐的口径

1. 三档挑战采用三组 NFT 的独立销毁，不作随机中奖承诺。
2. 个人三档与全局十阶段不能混为一个进度条。
3. 免费给 3 枚水果，不承诺直接满足三同。
4. 最高 1 亿只对应全局第一阶段第三档；后续按表递减。
5. 一钱包最多领取一档 Token 奖励，继续不累计或兑现旧档奖励。
6. 销毁不可撤销且不占份额，Agent 必须先解释再确认。
7. 55,000 是领奖份额，不是免费领取名额；1.43 万亿是玩家 cap，不是保证发满量。
8. 星星售完、奖励份额用完是两个独立条件。
9. LP 额度不结转，BNB 可以结转；购星成功和加 LP 成功分开显示。
10. 本次规则已经落入本地合约与公开玩法文案；编译、基础测试和 EVM 测试结果须单独记录，不把文案或单元测试当作主网部署或安全审计证明。
